# v5.2 预研：多平台直播与弹幕

> **2026-11-18 决定：这四个平台不再由本程序直接推流。**
> 画面统一走「本地取流」给的地址，用户自己填进对应平台的直播软件（直播伴侣 / OBS）。
> 本程序在这四家只负责弹幕。下面关于推流地址、门槛、拼法的内容保留作资料，
> 不再是产品路线。


> 调研时间 2026-11-18。目标平台抖音、斗鱼、快手、小红书。
> 本文只做技术可行性判断，不含实现。定稿前不发版。

---

## 一、结论先说

| 维度 | 判断 |
|---|---|
| 多平台同时推流 | **可行**，技术成熟，市场上已有 OBS 多路推流插件跑了两年 |
| 四家平台弹幕 | **可行但难度差异极大**，斗鱼简单，抖音和小红书是硬骨头 |
| 多平台弹幕合并到 PS5 | **可行**，现有 IRC 通道天生支持，只要往同一个口塞消息 |
| 最大风险 | 不是技术，是**平台协议变动**和**开源项目许可证** |
| 建议节奏 | 分三期，先斗鱼跑通再上抖音，别一次性啃四家 |

## 二、推流侧

### 四家都支持第三方推流

| 平台 | 推流入口 | 门槛 |
|---|---|---|
| 抖音 | 直播伴侣 → 推流码，或创作者中心 → 电脑直播 | **需 1000 粉或企业号**，这是唯一有硬门槛的 |
| 斗鱼 | 主播中心 → 推流设置，`rtmp://tx.douyu.com/live/` | 无 |
| 快手 | 快手直播助手 / 创作者服务平台 → 推流码 | 无 |
| 小红书 | 创作者中心 → 直播 → 电脑直播 → 推流码 | 无 |

**产品结论：推流地址让用户自己粘贴，程序不代取。**

理由：
1. 代取要登录态 + 各平台签名，是四份不同的工作量，还会随平台改版失效
2. OBS 多路推流插件（5.1k star，obs-multi-rtmp）就是让用户手动粘，市场验证过的做法
3. 推流地址属于敏感信息，经我们服务器中转反而增加风险，现在全程本地不过网

### 实现方式：多进程，不用 tee

现有 `core/relay.py` 是单路 ffmpeg。扩成 N 路，每个平台一个进程：

```
PS5 → 本机 rtmf 收流
        ├─ ffmpeg -c copy → B 站
        ├─ ffmpeg -c copy → 抖音
        ├─ ffmpeg -c copy → 斗鱼
        └─ ffmpeg -c copy → 快手
```

不用 ffmpeg 的 `tee` muxer，原因：
- tee 一个目标挂了容易拖垮整条管线，多进程天然隔离
- 现有 watchdog 逻辑（断了自动重连、最多重试 8 次）可以原样复用，每个平台独立计数

**Windows 上其实不用多进程。** rtmp-forwarder 的 `/api/config` 本来就接受
`forwarders` 数组，一次下发 N 个目标，它自己把一份流复制出去，零拷贝、
不占 CPU。2026-11-18 在打包机上实测过：下发两个目标，回读确认两个都在，
再下单个也对。所以 Windows 这条路上多平台的开销几乎可以忽略。

macOS（MediaMTX）和容器（nginx）没有这个能力，只能每平台一个 ffmpeg
从本机拉流再推。Mac 上实测能拉通（`rtmp://127.0.0.1:1935/app/<流名>`），
一路目标是假地址时只报 Connection refused 并自己重连，另一路照常推，
互不影响。

### 验证到了哪一步（2026-11-18 校准）

**四个自填平台的真实推流，一次都没推过。** 到目前为止验的是"转发链路自洽"，
不是"平台认可"：

| 项 | 怎么验的 | 结论 |
|---|---|---|
| B 站 | 长期实跑，v5.1.8 起一直在用 | 已验证 |
| 多目标转发 | rtmp-forwarder 下发两个目标并回读；一路填假地址时只那一路报错重连 | 已验证（接收端是本机模拟的） |
| 抖音/斗鱼/快手/小红书 真实推流 | 没做过 | **未验证** |
| 小红书 6 位码换地址 | 只确认接口会应答，没拿真账号换出过密钥 | **未验证** |

界面上的「地址怎么获取」是照着各家官方帮助中心和教程写的，不是亲手走完整流程。
其中"抖音推完还要回伴侣点开始直播"这一条，没有实测依据。

补验的顺序建议：快手（推流即开播、门槛低）→ 抖音 → 斗鱼 → 小红书。

### 两个必须写进界面的硬限制

**一、`-c copy` 不转码，所有平台码率相同**

PS5 推过来是多少码率，四家就都是多少。想给抖音降码率省流量，只能转码，CPU 立刻上来。
所以第一版统一码率，界面明确写「各平台码率一致，由 PS5 侧决定」。

**二、上行带宽是硬天花板**

总上行 ≈ 各平台码率之和 × 1.1。按 1080p 常规码率估：

```
B 站 8000 + 抖音 6000 + 斗鱼 6000 + 快手 4000 + 小红书 4000 ≈ 28 Mbps
```

家庭宽带上行普遍 30~50 Mbps，四家全开会顶到天花板，直接花屏掉帧。
界面应该实时显示「当前合计上行 X Mbps」，超过用户带宽就标红。

### 竖屏的坑

抖音、小红书推流默认竖屏（9:16），B 站、斗鱼是横屏（16:9）。PS5 是横屏画面。
推给竖屏平台要么上下加黑边，要么裁左右，观众体验都不好。
这个不属于技术问题，但产品上要提前说明，别让用户开播了才发现。

## 三、弹幕侧

### 难度排序

| 平台 | 协议 | 难度 | 说明 |
|---|---|---|---|
| 斗鱼 | 自有文本协议（STT），长连接 `danmuproxy.douyu.com` | **低** | 协议早年就公开，报文就是 `key@=value/` 拼接，心跳 `type@=mrkl/` |
| 快手 | WebSocket + protobuf，需要网页 cookie | **中** | 要带登录态，部分场景有滑块，community 有实现但不稳 |
| 抖音 | WebSocket + protobuf + **a_bogus 签名** | **高** | 签名算法要跑 JS，且平台会改。成熟实现不少，但是追逐战 |
| 小红书 | WebSocket + JSON 帧，游客态可听 | **中高** | 公开资料最少，能听但字段结构要靠抓包确认 |

### GitHub 上的现成项目

|---|---|---|---|---|---|
| xiaoyaocz/dart_simple_live | 16247 | Dart | 2026-08 | B站/抖音/斗鱼/虎牙 | GPL-3.0 |
| wbt5/real-url | 7831 | Python | 2024-06 | 58 个平台的流地址和弹幕 | GPL-2.0 |
| ihmily/StreamCap | 4434 | Python | 2026-09 | 多平台录制 | 未标 |
| saermart/DouyinLiveWebFetcher | 1905 | Python | 2026-09 | 抖音 | AGPL-3.0 |
| ape-byte/DouyinBarrageGrab | 1712 | C# | 2026-04 | 抖音 | 未标 |
| wushuaihua520/BarrageGrab | 429 | C# | 2026-10 | 抖音/快手/B站 | AGPL-3.0 |
| xifan2333/UniBarrage | 14 | Go | 2026-08 | 抖音/B站/快手/斗鱼/虎牙/小红书 | GPL-3.0 |

### 关键发现：16k star 的项目也没做快手和小红书

`dart_simple_live` 是目前最权威的多平台协议参考，它的核心库只实现了 **B站、抖音、斗鱼、虎牙** 四家，没有快手和小红书。

这说明快手和小红书不是"没人想到"，是"做起来不划算"。小红书的资料更是少到只能靠抓包。

### 许可证是硬约束

本项目是 **MIT**，上表里除了未标许可证的，**全部是 GPL-3.0 或 AGPL-3.0**。

结论：
- **不能抄代码**，只能参考协议行为自己重写
- **不能捆绑分发 GPL 二进制**（比如把 UniBarrage 打进安装包），否则整个组合的许可证义务会被拉进来
- 如果一定要用第三方二进制，只能让用户自己下载放进 tools 目录，程序检测到就用、没有就提示

### 建议：自己实现，只做 Chat 消息

我们需要的只有「观众说了什么」，不需要礼物、点赞、进场、关注。
这个范围比上面那些项目窄得多，自己实现的量是可控的：

| 平台 | 预估工作量 | 风险 |
|---|---|---|
| 斗鱼 | 1 到 2 天 | 低，协议稳定多年 |
| 快手 | 3 到 4 天 | 中，cookie 失效要引导用户重取 |
| 抖音 | 4 到 6 天 | 高，签名要嵌 JS 引擎，平台改版就得跟 |
| 小红书 | 3 到 5 天 | 高，资料少，得先花时间抓包摸协议 |

## 四、架构：多选还是单选

### 推流：多选

技术上没有障碍，一个收流端可以被多路 ffmpeg 同时读。
所以是**多选**，配上行带宽实时提示。

注意：如果用户只勾了一个平台，行为应该跟现在完全一样，不要因为改架构把单平台路径搞坏。

### 弹幕：多选，合并到一个口

PS5 那边看到的只有一个聊天室（Twitch 的 IRC），物理上就没有"分区显示"这回事。
所以多个平台必须合并成一路，按时间顺序推送。

需要处理的：
1. **来源标识**：PS5 的 IRC 消息格式是 `PRIVMSG`，可以带前缀。是否加「[抖]」「[鱼]」这类标记？加了信息量大但占字数，建议做成开关，默认关。
2. **限流**：四家同时来弹幕会刷屏。现有 `danmaku_throttle.py` 已经在管 B 站的节流，要扩成全局节流（合并后统一限速，而不是各平台各自限）。
3. **单平台失败不影响其他**：某个平台 client 断了，其他照推，界面上标一下哪个掉线了。

### 界面结构

现在是「本地取流 / 推 B 站」两个开关。改成：

```
输出到哪些平台
  [x] B 站直播间（已登录：xxx）
  [x] 抖音            [填推流地址]
  [ ] 斗鱼            [填推流地址]
  [ ] 快手            [填推流地址]
  [ ] 小红书          [填推流地址]
  合计上行 12.4 Mbps

弹幕来源
  [x] B 站
  [x] 抖音            [填房间号]
  [ ] 斗鱼            [填房间号]
  [ ] 快手            [填房间号]
  [ ] 小红书          [填房间号]
```

推流地址和弹幕房间号是两套东西，要分开放，别让用户以为填一个就行。

## 五、分三期走

**一期**：推流多平台 + 斗鱼弹幕
- 推流侧改造风险低，能立刻让「一个 PS5 推四个平台」这个卖点成立
- 斗鱼弹幕协议简单，把多源合并的架子搭好

**二期**：抖音弹幕
- 签名的坑最大，单独一期，失败也不影响一期已上线的功能

**三期**：快手 + 小红书
- 看二期的实际情况再定，小红书可能要用户提供账号做验证

**每期都要能单独发布**，某个平台挂了不能拖累整个版本。

## 六、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台改协议 | 该平台弹幕失效 | 每个平台 client 独立，坏了不连带；界面明确标"这个平台的弹幕暂时不可用" |
| 抖音签名变动 | 抖音弹幕断了 | 二期单独做，且做好随时下线的准备 |
| 上行带宽不够 | 全平台花屏 | 界面实时显示合计码率，超限标红警告 |
| PS5 推流码率固定 | 各平台码率不能单独调 | 第一版明说，后续要单独调就得转码，另算 |
| 用户拿不到推流地址 | 功能用不起来 | 界面里给每个平台的获取路径截图，照着点就行 |
| 账号风控 | 频繁连弹幕被限 | 加心跳间隔、异常退避，不做高频重连 |
