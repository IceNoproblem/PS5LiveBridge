# v5.2 自动开播与登录

> 2026-11-18 调研。结论先行，后面是依据和实测记录。
> 配套工具：`tools/probe_danmaku.py`（抓各平台弹幕原始帧，逆向时用）

## 一句话结论

四个平台做不到 B 站那种「勾选就自动开播」，也做不到 B 站那种扫码登录。
能做的按难度排：

| 平台 | 登录 | 拿推流地址 | 真实体验 |
|---|---|---|---|
| B 站 | 扫码（已有） | 开播接口（已有） | 勾选即开播，地址每次变 |
| 小红书 | 需手机 App 登录态 | 输 6 位验证码换密钥 | 半自动，比手动复制好很多 |
| 抖音 | 需 cookie | 网页创作者中心取，有时效 | 能自动，但接口签名会失效 |
| 快手 | 需 cookie | 网页取或官方 OpenAPI（要资质） | 同上 |
| 斗鱼 | 需 cookie | 主播中心，地址长期固定 | 粘贴一次长期用，其实最省心 |

想让四个平台都「像 B 站一样」，只有一条路走得通：**用系统浏览器自动化**，见第三节路线三。

---

## 一、B 站为什么能自动

两件事凑齐了：

1. `passport.bilibili.com/qrcode/getLoginUrl` 是**没有签名**的公开接口，扫码登录拿 cookie 很干净；
2. `api.live.bilibili.com/room/v1/Room/startLive` 用 cookie 就能换到推流地址，
   而且这个地址**每次开播都变**，用户不可能手动填，平台等于逼着你自动获取。

其他四家没有这两条。它们的登录接口都带签名或风控参数，签名算法写在混淆过的
JS 里，跟着前端发版变。

## 二、四个平台逐个说

### 小红书

推流地址是 `rtmp://live-push.xhscdn.com/live` 加一段密钥，但**密钥必须用手机 App
生成的 6 位验证码换**：

```
手机 App 预直播页 → 切「电脑」→ 拿到 6 位数字
    → www.xiaohongshu.com/zhibo 输入这 6 位 → 换到串流密钥
```

6 位码 12 小时内有效，每次结束直播再开都要重新生成。
第三方软件绕不过手机这一步，平台有意卡在这里。

**能做到什么**：界面上给一个输入框，用户把 6 位码填进来，程序调网页接口换密钥并自动填进推流地址。
用户动作从「复制两大段地址」变成「输 6 个数字」，这个体验接近自动。

### 抖音

推流地址在「直播伴侣 → 第三方推流」或「创作者服务中心 → 直播管理」里，有几个硬约束：

- 地址带 `expire` 参数，网页端拿到的有效期大约 2 小时到 24 小时（不同入口说法不一）；
- 直播结束即失效，下次开播要重新取；
- 接口要 `a_bogus` 签名，算法在 JS 里，社区有纯 Python 实现但会过期；
- 第三方推流有粉丝门槛（一般 1000 粉或企业号）。

**能做到什么**：如果签名跟得上，可以做到接近自动。但这是个需要持续维护的活，
签名一变就得跟。稳不住的话不如退回「粘贴一次，过期提醒」。

### 快手

有**官方 OpenAPI**：`pushUrls` 接口取推流地址，`stopPush` 结束直播。听起来最正规，但前提是：

1. 在快手开放平台完成入驻；
2. 创建应用拿到 `app_id` / `app_secret`；
3. 走 OAuth 拿到用户授权。

普通主播不会为了开个播去注册开放平台应用。所以这条路只适合做产品的公司，不适合个人工具。

网页端（快手直播助手 / 创作者服务平台）也能看到推流码，但那同样要登录态和签名。

### 斗鱼

主播中心 → 直播设置里的推流地址是**长期固定**的（`rtmp://sendtc.douyu.com/live/<key>?wsSecret=...&wsTime=...`），
不像 B 站每次变。

**能做到什么**：粘贴一次，存下来反复用。地址失效时给个提示和直达链接。
这是四个平台里最省事的一个，甚至不需要自动开播。

## 三、三条路线

### 路线一：地址库（成本最低）

每个平台存一份推流地址，开播时自动套用，失效时提示「去平台重新取」。

- 工作量：小。`OUTPUTS` 已经存了地址，补上「失效检测 + 一键直达」即可
- 稳定性：高，不依赖任何平台接口
- 体验：第一次要手动复制，之后都是勾选即用
- 适合：斗鱼（地址本来就长期有效）、以及所有平台的兜底

### 路线二：单平台接口逆向（成本中等，会烂）

小红书 6 位码、抖音网页取地址，都属于这一类。

- 工作量：每个平台 3 到 5 天，还要持续跟版本
- 稳定性：低，平台改一版就得修
- 体验：接近自动

建议只做小红书。因为它的 6 位码接口相对稳定（就是给第三方推流用的），
而且用户动作简化最明显。抖音的签名战不值得跟。

### 路线三：系统浏览器自动化（成本高，体验最好）

不逆签名，直接让平台自己的 JS 干活：程序启动一个带调试端口的浏览器，
打开平台创作者中心，用户在里面登录（扫码或账号密码都行），
程序用 CDP（Chrome DevTools Protocol）点「开始直播」、抓页面上的推流地址。

关键优势：

- **签名问题不存在**，所有请求都是平台自己的页面发出的
- 扫码登录也顺带解决，用户在真浏览器里扫，程序读 cookie 就行
- 平台改版最多是选择器变了，比签名算法好维护

关键代价：

- Windows 自带 Edge，Mac 上大多有 Chrome，**不用打包 Chromium**，只连已有的浏览器
- 需要处理「用户没装浏览器」「浏览器正在被用户使用」这些情况
- 无人值守的 NAS 容器版用不了这条路（没有桌面环境）

技术上就是 `msedge --remote-debugging-port=9222` 加 `websocket` 调 CDP，
不需要 Playwright 那一套几百 MB 的依赖。

**如果目标是「四个平台都像 B 站」，这是唯一现实的路线。**

## 四、弹幕：按房间号就能拿，不需要登录

这条先纠正一个错误结论。2026-11-18 上午我试斗鱼，用网上流传的 4 字节包头，
服务端连上就断，于是判断「协议已变、四个平台一起做不现实」。
**这个判断是错的。** 下午翻了 GitHub 上在维护的项目，发现包头早就是 **12 字节**了，
改过来当场就通了。

教训：平台改协议，GitHub 上一定有项目跟着改。自己照着老资料试不出来就下结论，
等于把自己的试错当成平台的现状。

### 斗鱼（已完成）

参考 `flxxyz/douyudm`（86★，MIT，2026-11-07 更新）。协议全貌：

| 项 | 值 |
|---|---|
| 地址 | `wss://danmuproxy.douyu.com:8501-8506` 任一端口，连不上换下一个 |
| 包格式 | 12 字节头：长度(4) 长度(4) 689(2) 0(2)，长度填「总长减 4」 |
| 正文 | `key@=value/` 文本，value 里的 `/` 编码成 `@S`，`@` 编码成 `@A` |
| 登录 | 连上直接发 `loginreq` + `joingroup`，不等 loginres |
| 心跳 | 45 秒一次 `mrkl`；服务端发 `pingreq` 也要立刻回 |
| 房间号 | 靓号（6657 这种）要换成真实号，否则收得到 loginres 但一条弹幕都没有 |
| TLS | 默认参数会被拒，要锁 TLS1.2 且 `SECLEVEL=1` |

实测：房间 74751，10 秒收到 `chatmsg`、`uenter`、`dgb`、`ranklist` 等消息，
真实弹幕内容「想起名字就头痛：哈啊哈哈6666」。靓号 6657 正确解析到 6979222。

不需要任何账号，填房间号就行。已经写进 `core/danmaku_douyu.py`。

### 抖音

`jwwsjlm/douyinLive`（550★，**MIT**，2026-10-23）是现在最完整的实现，
LiveTap（MIT）直接把它当内核。它的 README 写得很明确：**以观众身份只读接收公开直播间**，
用游客 Cookie 就够，不需要登录。

难点是要移植两块：

- `a_bogus` 签名：SM3 + RC4 + 变体 Base64，纯算法不依赖 JS，Go 代码几百行
- 弹幕协议：WebSocket + protobuf push frame + gzip

许可证是 MIT，可以看到算法自己用 Python 重写。工作量估 1 到 2 天。

### 快手

搜到的实现全是 AGPL-3.0（`BarrageGrab` 429★、`simple-live-kuaishou` 37★），
**代码不能抄进这个 MIT 项目**。协议本身是 WebSocket + protobuf，还要 `__NS_sig3` 签名，
没有 MIT 的实现可以参照，只能自己啃。

### 小红书

`Sky-senge/xhs-danmaku`（MIT，2026-11-12）的路子是「旁听直播助手的 WebSocket」，
不再自己算签名。这条路对小红书成立，因为小红书的直播页本来就有一个给直播助手用的 WS。

### 三个平台的对比

| 平台 | 有没有可参考的 MIT 实现 | 主要成本 |
|---|---|---|
| 斗鱼 | 有，已落地 | 无 |
| 抖音 | 有（douyinLive） | a_bogus + protobuf，1~2 天 |
| 小红书 | 有（xhs-danmaku） | 旁听 WS，比抖音轻 |
| 快手 | 没有（只有 AGPL） | 要自己逆签名 |

## 五、第三方软件：没有能自动登录开播的

2026-11-18 在 GitHub 上按「直播推流」「开播 推流码」「多平台推流」扫了一遍。
能给这四家做「登录后自动取推流码并开播」的现成软件，没有。

找到的分三类：

1. **B 站的**：`chenxi-Eumenides/bilibili_live_tool`（132★）这类，扫码登录、取推流码、开播都有。
   但 B 站我们自己做完了，接口是开放的，所以生态才这么全。
2. **OBS 插件**：`sorayuki/obs-multi-rtmp`（5167★），一个 OBS 同时推多个平台。
   但地址还是得你自己从各平台后台复制，它只解决「一路变多路」。
   这个能力我们的 rtmp-forwarder 已经有了，不需要它。
3. **浏览器自动化中控台**：`hotdogarea/boleme_living_controller`（11★，MIT），
   打开浏览器让你登录，然后替你在中控页面上发弹幕、点讲解。不推流。

另外「播了么」生态里有个 iPhone 直推插件，思路是电脑把画面推给手机、由手机开播。
这绕开了「拿推流码」这件事，代价是要多一部手机。

一个旁证：连商业化的中控工具也只能做到「开浏览器让你登录，然后替你在页面上点」，
说明浏览器自动化就是这条路的天花板，没有更捷径的接口。

## 六、四个平台给 OBS 的推流方式

OBS 本身没有任何平台特殊处理，它就是个通用 RTMP 客户端：
「服务器地址」+「串流密钥」两个框，填什么就连什么。
所以「OBS 怎么推这四个平台」等于「这四个平台发的是什么地址」。

| 平台 | 服务器地址 | 密钥形态 | 从哪拿 | 有效期 |
|---|---|---|---|---|
| 抖音 | 每场不同，带 `expire` 参数 | 一串字符 | 直播伴侣 → 第三方推流；创作者中心 → 直播管理 | 2 到 24 小时，下播即废 |
| 斗鱼 | `danmupro` / `sendtc` 两个域名都见过，不固定 | 短串 | 主播中心 → 直播管理 → 推流设置 | 长期，重置才失效 |
| 快手 | **固定** `rtmp://live.kuaishou.com/live` | 推流码 | 直播中心 → OBS 推流；创作者服务平台 | 较长 |
| 小红书 | **固定** `rtmp://live-push.xhscdn.com/live` | `流ID?txSecret=…&txTime=…`（腾讯云 CDN 鉴权） | 手机 App 拿 6 位码，去 xiaohongshu.com/zhibo 换 | 6 位码 12 小时有效，密钥跟场次 |

### 我们怎么接的

地址里有两段信息：服务器 + 密钥。OBS 让人填两栏，我们只让人填一栏。

- **小红书、快手**：服务器固定，界面上只出现「粘贴推流密钥」，前缀我们补
  （`core/platforms.py` 的 `server` 字段 + `full_url()`）
- **抖音、斗鱼**：地址不固定，还是整条粘
- 两种都认：用户整条粘进「只填密钥」的框里也不会出错，`full_url()` 看到 `rtmp://` 就原样用

拼出来的地址交给 `split_full_url()` 拆成 host / app / stream，
rtmp-forwarder 按这个 publish，行为和 OBS 完全一致。

### 还能再往前一步

小红书那步「拿 6 位码去网页换密钥」是可以自动化的：
带上 xiaohongshu.com 的登录态调换密钥接口，用户只需要在界面里输 6 个数字。
前提是要有小红书的 cookie，这条留到后面单独做。

## 七、三家是怎么开播的

「拿到推流地址」和「直播间上线」是两件事，各家顺序不一样，这决定了能不能全自动。

| 平台 | 流程 | 推流就等于开播吗 |
|---|---|---|
| B 站 | 调开播接口拿码，推流后自动上线 | 是 |
| 快手 | 拿推流码，推流后平台检测到流就自动开播（官方 OpenAPI 文档原话） | 是 |
| 抖音 | 拿码，推流，**还要回后台点一下「开始直播」** | 不是，两段式 |
| 斗鱼 | 主播中心点「开始直播」**才生成推流码**，推上去就上线 | 不是，得先开播 |
| 小红书 | 先推流，**再回手机 App 点「进入直播」** | 不是，手机必须参与 |

所以「勾选就自动开播」这件事：

- **B 站**：全自动，已在做
- **快手**：只差拿推流码这一步。有官方 OpenAPI，但要在开放平台入驻建应用
- **抖音**：就算拿到码，还得有人在后台点一下，除非用浏览器自动化代点
- **斗鱼**：同理，先得点「开始直播」，点了才有码
- **小红书**：手机那一下绕不过去，连官方教程都写「一定要先推流再去手机点」

### 小红书那一步已经能自动了

从开播页的 JS 里挖到了接口，实测不带 cookie 时返回「无登录信息」而不是签名错误，
说明这组接口只校验登录态，不需要 `x-s`：

```
GET /web_api/sns/v1/live/obs/host_auth_info   查有没有电脑开播权限
GET /web_api/sns/v1/live/obs/push_url?code=   6 位数字换串流密钥
GET /web_api/sns/v1/live/obs/living_push_url  正在直播时取当前地址
```

返回里 `mainPushInfo.streamKey` 就是要填的那串，本身带 `txSecret` 鉴权参数。

已经做成功能（`core/xiaohongshu.py`）：用户在界面填一次网页 cookie，
之后每次开播输 6 个数字，程序自己换地址并填进配置。
剩下「手机点进入直播」这一步平台有意留给手机，绕不过。


## 九、抖音弹幕：两把锁，都是纯算法

斗鱼填个房间号就通了，抖音多两道，而且**两道都和浏览器无关**，
所以容器版照样能用。2026-11-18 实测记录：

### 第一道：web_rid → room_id

用户给的是直播间链接后面那串（web_rid），弹幕要的是内部 room_id。
换算接口是 `/webcast/room/web/enter/`，**必须带 a_bogus**，否则返回 200 但正文为空。

a_bogus = SM3 + RC4 + 变体 Base64，结论：

| 项 | 值 |
|---|---|
| 参与签名的 | 实际发出去的那串查询参数，**顺序不能变** |
| UA | 必须和请求头一致，否则算出来对不上 |
| 输出 | 一百七十来个字符，末尾带一个 `=` |
| 拼进 URL | 要整体 URL 编码（`+` `/` `=` 都得转），并放在参数最后 |

参数集合照抄网页端：`enter_from=link_share`、`browser_name=Chrome`、
`browser_version=133.0.0.0`、`os_name=Windows`、`os_version=10`、`room_id_str=`、`msToken=`。

### 第二道：WebSocket 握手

`wss://webcast100-ws-web-lf.douyin.com/webcast/im/push/v2/`，要两个东西：

1. `signature`：16 个字符，同样是 RC4 + 变体 Base64，但输入是 13 个字段拼起来的
   MD5（叫 X-MS-STUB），字段清单在直播间页面里就能读到（`websocketKey`）：
   `live_id, aid, version_code, webcast_sdk_version, room_id, sub_room_id,
   sub_channel_id, did_rule, user_unique_id, device_platform, device_type, ac, identity`
2. `Cookie: ttwid=...`：**缺它服务端返回 200 不给升级**，看起来像签名错，其实是 cookie 错

ttwid 从 `https://live.douyin.com/` 的响应里就能拿到，有效期很长，取一次够用。

### 帧格式

| 项 | 值 |
|---|---|
| 外层 | PushFrame：`payload_type(7)` 是 `msg`/`hb`/`ack`，`payload(8)` 是正文 |
| 正文 | 优先 gzip，解压后是 Response，`messages(1)` 才是业务消息 |
| 消息 | `method(1)` + `payload(2)`，method 决定解哪种 |
| 心跳 | 10 秒一次 `PushFrame{payload_type:"hb"}`（即字节 `3a 02 68 62`） |
| ACK | 帧头有 `im-internal_ext` 就回 `PushFrame{logid, type:"ack", payload:ext}`，不回会慢慢断流 |

### 字段编号（踩过坑，记下来）

| 消息 | 字段 |
|---|---|
| 聊天 | `user(2)` + `content(3)` |
| 用户昵称 | **`User.nickname(3)`**，网上流传的 2 是错的；头像是 `9/10/11` |
| 礼物 | `repeat_count(5)` + `user(7)` + `gift(15)`，名字在 `GiftStruct.name(16)`，其次 `describe(2)` |

昵称**匿名访问下会被平台打码**（「茶***」「S..」这类），弹幕正文完整。
要完整昵称只能带自己的 cookie，这一版没做。

### 已经落地

`core/douyin_sign.py`（SM3 + a_bogus + 握手签名，SM3 用官方测试向量核对过）
和 `core/danmaku_douyin.py`（不依赖第三方 protobuf 库，自带一个小解码器）。
界面第 5 步多了「弹幕来源」一块，抖音、斗鱼可勾，快手和小红书如实标「暂不支持」。

## 十、建议的落地顺序

1. **斗鱼弹幕已落地**（2026-11-18）：填房间号就能拉，不需要账号。
2. **抖音弹幕**排下一个。有 MIT 的内核可以照着写，成本主要在 a_bogus。
3. **地址库**：四平台推流地址持久化 + 失效提示。所有方案的底座，即使以后做了自动开播也照样有用。
4. **小红书 6 位码**：用户动作从两大段复制变成输 6 个数字。
5. **浏览器自动化**（路线三）作为 v5.3 的方向评估，它是唯一能让四平台都「像 B 站」的方案。
